# 任务索引、并发与故障恢复

## 哪一张表才是任务清单

`evidence` 保存多种业务记录，并非每行都是任务：工作流使用 `workflow:` ID，此外还有识别证据、AI 队列、资源检查、目录扫描摘要等。因此它的总行数通常大于任务数。

`workflow_overview` 是全部 `workflow:` 记录的轻量投影，包含普通专辑、批次、活动、隐藏和已结束记录；不是滚动窗口，也没有延迟同步。SQLite 的插入、更新、删除触发器在同一事务内维护它。升级发现列结构不同会在事务内重建并回填；中断不会提交半个索引。隐藏任务保留投影，由查询条件排除。

`next_job()` 先查投影的状态、暂停、到期时间和前置依赖，只读取选中任务的完整 JSON。`resume_stage`、完整配置和文件清单保存在 `evidence.payload`，不属于 overview 的列，不能直接 `SELECT resume_stage FROM workflow_overview`。

无筛选时，`SELECT COUNT(*) FROM workflow_overview` 应等于 `SELECT COUNT(*) FROM evidence WHERE id LIKE 'workflow:%'`；界面的专辑总览还会合并识别、搜索和处理链，所以界面项目数可以更少。不要通过手工删除投影行清任务，应使用任务中心。

## 运行策略

- 识别、搜索及各专辑私有整理副本有最多 4 个工作槽。元数据任务不再固定只能占 2 槽；同一 PT 站点仍有自己的请求锁。
- 发布、完整校验、补全和入库收尾可与独立的轻任务同波执行；大任务尚未结束时，空出的轻任务槽会继续领取任务。令牌消费和旧音源移出仍遵循串行阶段与事务约束，不会并发重放。
- 等待超过 10 分钟的 `enrich` 会提升选择优先级，防止长尾补全任务长期得不到处理。
- 执行前刷新当前 `catalog`、`ai` 和“按音乐人整理”策略；下载前的识别/搜索任务还刷新 `quality`。原任务路径、下载器身份和其他不可变配置保留。已经准备或发布的音频不会因修改音质偏好而重新解释。
- 首次升级会保留旧批次手工关闭的 AI / 网页兜底，防止为几千条任务突然恢复付费调用。后续仅在对应策略发生变化时同步，保存无关设置不会恢复这些旧开关；手动重试任务也可明确采用当前配置。
- 仅用 API 批量识别：在连接与设置里关闭公开网站兜底和 AI。修改后会作用于已有任务的下一阶段，无需重建批次；正在进行的请求在其超时/检查点结束后生效。

## 慢、暂停与故障的区分

`profile/state/worker-health.json` 每 5 秒更新，独立于数据库写锁。它包含进程 PID、队列线程是否存活、当前任务、最近安全检查点及其时间、存储恢复异常。心跳代表进程仍响应，不能用来冒充文件处理进度；检查点时间长时间不动表示某个子步骤较慢，仍须结合阶段、超时和文件事件判断。

工作流保留 `stage_started_at`。桌面任务中心显示最近安全检查点距今秒数，并明确显示等待存储恢复的状态。Docker `/healthz` 会在心跳过期、队列线程死亡或存储恢复失败时返回 503，而不是仅因网页端口正常就报健康。

数据库忙等待统一为 30 秒，单条幂等状态写入仅对 BUSY/LOCKED 做有限重试；磁盘 I/O 错误和损坏不会被当作锁冲突掩盖。队列异常后的恢复写入如果也失败，会保留恢复上下文并退避，不退出队列线程，也不重放已完成的外部动作。中断阶段进入核对，不能仅凭“运行超过十分钟”就启动另一份文件发布或令牌请求。

## Windows 进程退出取证与监督

GUI 和 worker 启动、退出、未处理异常位置记录在 `state/lifecycle.jsonl`；原生 Python 故障栈写入各自的 `*-fault.log`。进程被强制终止、整台机器断电或蓝屏时，退出钩子不保证执行；有启动而没有退出记录是排查线索，不是证明具体根因。

正式 Windows 程序会启动独立隐藏的 worker 监督脚本，按实际 EXE 和运行档案检查进程，缺失时拉起，单档案互斥。最多每 10 分钟启动 5 次，达到限制后退避；记录在 `state/supervisor.jsonl`。优先使用 Windows 作业对象的 breakaway 标志，环境不支持时回退普通子进程。它不能保证逃离禁止 breakaway 的外层进程监管，也不能修复机器级驱动/内存问题。

“退出应用及后台”和更新交接先写 `state/supervisor-stop`，监督脚本不会把这类正常停止当故障重启。重新打开软件会恢复监督。安装器提供可选的“登录 Windows 后自动启动”，默认不勾选，升级保留安装任务选择。没有勾选时，系统重启后仍需手动打开应用。

## 日志体积与安全维护

新增交易 `plan_id`、事件 `task_id/tx_id`、专辑目录和名称候选索引。按任务查事件请使用 `task_id` 与 `seq`，不要在整个事件 payload 上执行 `%job_id%` 扫描。

后台空闲时每天最多归档一批 30 天前的常规排队、完成和暂停事件（每批 1000 行）。先写完整 gzip 并 fsync，再删除对应事件。文件发布、令牌、事务与错误审计保留在 SQLite；压缩日志在 `state/event-archives`，仍属于私人运行档案。归档后 SQLite 会复用空页，不会自动缩小主文件，避免在线 VACUUM 长时间占写锁。

运维可通过共享 CLI 手动归档更多批次：

```sh
docker exec musicops python -m musicops.cli --base /config/profile archive_events --payload '{"days":30}' --wait
```

容器名按自己的 compose 配置替换。每次最多 1000 行；返回 `more_possible=true` 时可再次执行。不要删除仍被任务引用的恢复副本，也不要直接把临时 SQL 补丁反复叠加到已升级源码。

## 既有专辑与源文件清理

专辑名称候选按艺人、繁简、空格和标点归一化建立索引，与目录命名方式无关。名称只用于寻找候选，不直接证明同一发行；桌面与网页都会明确提供“补入既有目录”或“保留独立版本”的选择。补入不覆盖已有录音；同名录音时长冲突、多份既有录音或过期索引会停止并说明原因。库中已有重复目录仍通过去重合并页面扫描、确认和可恢复合并。

外部修改了已入库文件时，只有重新通过完整音频解码、曲名/艺人和时长核对，才以 `completed` 加 `warnings` 记录“保留原始下载”，继续更新音乐服务器索引。文件缺失、损坏或录音身份改变仍需核对，不会将其标成成功。

## 验收边界

合成回归覆盖并发、状态恢复、索引查询计划、认证熔断、目录候选、归档和界面。它不代表真实 PT 登录/FL 消费、整库人工封面鉴定、所有外部音乐服务器已完成扫描，或 Windows 静默退出根因已被证明。Plex 已有的独立扫描守护方案不由 MusicOps 覆盖或重启。
