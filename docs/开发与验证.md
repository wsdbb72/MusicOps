# 开发与验证

本文记录 **MusicOps 0.4.2** 的实现约定和验收方式；测试数据与真实账号、音乐库验收分开。

应用由 PySide6 GUI、独立 worker、SQLite 状态、域名绑定的系统凭据保护和服务适配器组成。GUI 通过本地 IPC 提交任务，长任务在后台执行。

Windows 使用当前账户 DPAPI、命名管道与文件锁。macOS 使用 Keychain 保存 AES-GCM 主密钥，本地档案只存认证加密后的秘密文件；IPC 使用带密钥认证的 AF_UNIX，私有目录权限为 `0700`，socket 为 `0600`。两端均不提供明文凭据存储回退。macOS 默认档案位于用户 Application Support，不写入 `.app`。

| 位置 | 职责 |
| --- | --- |
| `src/musicops/gui` | 三个工作流入口、任务中心、配置向导 |
| `src/musicops/worker` | 本机 IPC、后台生命周期、单写者保护 |
| `src/musicops/app/pipeline.py` | 批次准备、识别 / 搜索 / 处理记录、批量控制、阶段推进与恢复 |
| `src/musicops/app/recognition.py` | 常规失败后的有界 AI 别名检索与真实候选推荐 |
| `src/musicops/app/search_status.py` | 站点结果分类、独立故障与可用来源汇总 |
| `src/musicops/providers` | 十个平台歌单、文件导入、站点、歌词、资料、下载适配器 |
| `src/musicops/clients` | qBittorrent、Navidrome、凭据与网络边界 |
| `src/musicops/library`、`media` | 索引、路径、事务、标签、NCM、音频验证 |
| `tests` | 合成样本、模拟服务与回归验证 |
| `packaging` | Windows 文件夹包 / 安装器、原生 macOS `.app`、运行包验证 |

## 本地开发

使用 Python 3.12 或以上版本创建虚拟环境，安装 `requirements.lock` 与可编辑工程。命令见 [README 开发部分](../README.md#开发验证与贡献)。

测试使用临时目录和模拟服务；媒体验证测试需要可用的 FFmpeg／ffprobe。GUI 测试可以设置 `QT_QPA_PLATFORM=offscreen`，Windows 凭据相关验证依赖当前账户的 DPAPI。避免把测试档案指向自己的实际音乐库。

`config/example.json` 展示通用配置形状。实际服务地址、鉴权与音乐目录应在本地档案中配置。可运行 `scripts/export_config_schema.py` 重新生成公开配置示例与 JSON Schema。

macOS 源码开发可使用：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r packaging/requirements-macos.txt
.venv/bin/python -m pip install --no-deps -e .
.venv/bin/musicops-gui --base "$HOME/Library/Application Support/MusicOps/dev-profile"
```

Windows 与 macOS 的依赖文件分别锁定对应构建环境。使用独立开发档案，避免与已安装应用同时操作相同私人档案。

## 证据边界

`index_library(..., metadata_only=True, checkpoint=...)` 返回元数据级只读证据，音频 SHA256 保持空值，解码状态为未运行。扫描通过检查点报告进度并响应取消或暂停；不能把快速索引当作完整音频验证。原始标签摘要有大小预算，二进制封面不会在任务结果中展开。

开始工作流应先保存可见的批次准备记录，再进入本地目录扫描和需求对比。`scanned_count` 统计本地音频文件，`selected_target_count` 表示本批歌单选择；消息明确标识单位，不得把扫描数写成歌单已检查数量。GUI 要能读取准备进度、失败和取消结果；异步 IPC 已接受、库扫描结束、专辑入库完成属于不同状态。

识别完成后创建确定 ID 的独立搜索记录，选定资源后再创建后续处理记录，避免重启或重试重复创建同一交接任务。任务中心使用 **识别任务 / 搜索任务 / 下载与入库** 分类并按需读取曲目详情；前一阶段的完成结果保留。独立的手动目录识别和四站搜索也应可追溯。

`bulk_workflows` 只接受暂停、继续、取消和 1–500 个真实任务 ID，逐项返回状态。暂停勾选任务在当前阶段结束后生效；取消不回滚已完成发布或停止做种。批次准备可控制关联的未终结任务；需要核对或已结束的任务不通过批量继续重放。GUI 翻页保留勾选，页面与分类全选只选择当前页。批量 AI 解释最多使用前 20 项的必要摘要，并明确截断范围，不发送整批曲目。

文件名与标签冲突、缺少发行信息、版本不一致、时长不明或未完成完整解码时，匹配保持待复核。在线资料候选与音频完整性验证是独立证据。

公开测试使用合成歌单和虚拟域名。新增服务适配器时应测试请求白名单、响应大小、超时、取消、鉴权失败、身份冲突与部分响应，不在测试中嵌入实际 Cookie 或密钥。

平台曲目 ID 必须保留来源命名空间，文件导入 ID 缺失时只生成本地稳定目标标识。跨平台网易云引用要经过独立的歌曲、艺人、专辑与时长匹配，不能把外国平台数字 ID 当作网易云 ID。XLSX 只读导入不得执行公式、宏、外部关系或解压到任意文件路径。格式与许可参考见 [歌单读取记录](references/global-playlists.md)。

## 自动识别与搜索的回退规则

普通目录结果先尝试完整发行和曲目核对；只有不能得到唯一可靠结果时，才进入已配置且启用的 AI 兜底。`RecognitionFallback.identify` 可复用已有 `found`，避免重新查询同一普通结果。新密钥在设置向导中默认启用 AI，用户可关闭；缺失密钥、离线或未配置模型时不发模型请求。

每次识别最多两次模型调用、两个去重替代查询，选择上下文最多 20 个真实候选。AI 可规范名称、别名和署名，随后调用既有 MusicBrainz / Discogs 查询；模型只能返回实际候选 ID、置信和理由，不能生成录音 ID、网址或标签写入指令。文件名提示只保留 basename，发送内容使用字段白名单，不发送整个状态、库目录或凭据。未知候选、低置信、多版本歧义和已知时长冲突不自动采纳。推荐仍标记为未确认，由本机完整证据核对决定后续步骤；AI 异常保留常规候选，取消必须继续向上传播。

资源站检索没有匹配时，可使用真实目录推荐的规范名称重搜一次；新的检索词不能更改原身份约束，艺人或发行不一致时仍需核对。AllMusic、Rate Your Music、Album of the Year、VGMdb 保留人工检索链接，搜索链接本身不当作已抓取的身份证据。

各站请求和状态独立：`NO_RESOURCE` / `NO_MATCH` 是正常空结果，鉴权、限流和网络错误只影响该站。其他来源继续，成功结果保留。可用来源没有匹配且开启回退时，歌单任务可以进入网易云；全部已启用来源均不可用时等待检查。不将不可用、未启用或未返回页面表述为“四站均无资源”。没有启用任何 PT 来源且歌单已开启网易云回退时，直接交接网易云处理，不调用 PT 或 AI；回退关闭时提示配置，保持向导可跳过账号的行为。

相关合成回归位于 `test_ai_recognition.py`、`test_ai_fallback_integration.py`、`test_search_resilience.py`、`test_task_controls.py` 和 `test_task_center.py`。覆盖 API 默认接入、取消、未知 ID、已知匹配不花 AI 调用、别名不越过原身份、独立站点故障、批量任务及树形明细；这些测试不能替代真实账号或真实音源验收。

## 打包

正式发布使用 [`desktop-release.yml`](../.github/workflows/desktop-release.yml)：增加版本后推送 `codex/release-*` 分支，或手动运行该工作流。Windows 全套回归必须实际执行六项原生安装测试，冻结程序还需通过入口与批量操作验收，以及 `smoke_windows_installer.py` 的九项完整运行包安装、更新、重装和卸载检查。Mac 复用两架构构建，在原生 runner 验证应用、钥匙串、安装与重装。

只有所有平台成功，聚合任务才核对三份构建清单的版本、提交、七个核心产物和 SHA-256 / SHA-512，并生成对应提交的源码 ZIP、校验文件，创建草稿、上传、核对服务器散列后公开 Release。标题仅为 `MusicOps X.Y.Z`。已有同版本 Release 不覆盖；上传或核验失败保留草稿供排查。普通开发分支的测试与 Mac 产物仍不自动公开；`codex/release-*` 则只走完整发布流程，避免重复构建。发布完成后将相同已验证提交同步到 `main`。

`packaging/build_windows.ps1` 生成 Windows 文件夹包。源码仓库不分发 FFmpeg 等第三方媒体工具二进制；如自行加入工具，应收集与具体版本匹配的许可证、来源及必要对应源码。

Windows Inno 安装器先查现有安装记录、常见目录或有效快捷方式；检测到后更新原目录，手选既有绿色版目录也按更新处理。保留 `profile`、`tools`，拦截已知降级和把已登记安装改装到另一目录；文件被占用则要求安全退出后重试，不杀进程、不代替用户取消任务。`tests/test_windows_installer.py` 使用独立测试 AppId 和合成可执行文件验证真实首次安装、更新、绿色版、降级、路径与运行中后台拦截，不读取实际用户安装记录。需要 Inno Setup 6.5 或更新版，可通过 `INNO_ISCC` 指定编译器；缺少原生环境时跳过须如实记录。

运行包验证应使用新建临时档案，确保首次启动、GUI／worker 通信、设置保存和失败场景均可复现。`smoke_formal.py` 与 `smoke_workflows.py` 用于原生运行包验证；具体参数可查看各自的 `--help`。构建日志、个人运行报告和配置档案属于本地内容，不提交公开仓库。

macOS 必须在对应架构的真实 macOS runner 构建，不从 Windows 交叉打包后宣称可运行。`packaging/build_macos.py --arch arm64 --output dist/macos` 生成 Apple Silicon 包；Intel runner 使用 `--arch x86_64`。脚本检查 `.app` 身份、架构、ad-hoc 签名，使用 `pkgbuild` / `productbuild` 生成原生安装器，再生成 ZIP、PKG、SHA256 / SHA512 与提交对应的构建清单。

`smoke_macos.py` 验证独立运行包（含并发后台轮询）；`smoke_macos_installer.py` 只在一次性的 GitHub Mac runner 执行，用真实 `installer` 安装到 `/Applications`，检查 root 所有权、签名、收据、运行中后台的替换拦截、重复安装移除过期文件，以及配置和加密凭据保留。最后从已安装的应用再次运行完整验收；当前要求 29 项具名运行证据，增加成功检查不会因旧的固定计数误报，缺少或失败任一必需检查仍阻止发布。安装器 payload 只有应用，第三方许可包含在签名前的资源中，不写入用户档案或钥匙串，不自动启动 root 应用。

macOS 包目标为 15.0 及以上；当前不包含 Developer ID Application / Installer 签名或 Apple 公证。ad-hoc 签名只覆盖应用完整性，PKG 未签名，不代表 Apple 对开发者身份或内容作了公证。安装器拒绝符号链接目标和不匹配的芯片类型，并要求已有 MusicOps 进程完全退出。

## 同步仓库与发布

用户可见的修复或改进完成后，同步源码仓库、中文 README 和操作文档，并发布新的 Release。标题只用 **MusicOps 版本号**，例如 **MusicOps 0.4.2**，变更说明放正文。CI 仅负责验证，发布过程需要单独完成，不能把“已推送提交”写成“安装包已更新”。

每次发布核对：

1. 改动、版本号、操作说明和截图一致；回归测试通过。
2. 从明确的源码提交构建 GUI、worker 和安装器，使用临时档案验收运行包。
3. 检查源码、运行包和安装器不含真实凭据、个人档案、音乐、种子缓存或私人服务地址；收集第三方许可。
4. 使用版本标签导出源码包，生成 Windows 安装包、便携 ZIP 和对应 `SHA256SUMS.txt`。
5. 推送提交与标签，确认 Windows 测试与 macOS `arm64` / `x86_64` 构建结果；每次 Release 同步两种 Mac 包，不能把只有流水线定义当作已有运行包。
6. 创建匹配 Release，挂载两种系统中与标签一致的资产，包含 Windows EXE / ZIP、Mac `arm64` / `x86_64` 的 PKG / ZIP、源码 ZIP 与校验文件。Mac tag 发布任务会检查版本、提交、架构、自检与哈希后上传到已存在的 Release。
7. 核对服务端文件名、大小、SHA256 及 Mac 构建清单，确认公开下载可用后再宣布发布；失败的架构必须如实报告，不能标为已验证。

软件图标与工作台截图属于公开资产。截图采用合成资料，不能包含个人路径、账号、歌单、鉴权或实际私人任务。

## GitHub Actions

Windows 测试工作流使用 Python 3.12、锁定依赖与合成测试。Chocolatey 只在临时 CI runner 中安装 FFmpeg／ffprobe，不打包或上传媒体工具、运行档案与个人报告；该测试工作流本身不发布安装包。

[`macos-release.yml`](../.github/workflows/macos-release.yml) 使用 `macos-15` / `macos-15-intel` 原生矩阵。开发分支推送和手动运行保存构建产物；`v*` 标签在两种架构构建通过后，校验版本 / 提交 / 完整性，再将 Mac 包上传至同标签的已有 Release。打包验收使用临时隔离钥匙串与新档案，不读取用户音乐库，不执行真实下载或 FL 使用。构建产物和现场真实服务验收分开说明。

配置参考 [GitHub Python 测试指南](https://docs.github.com/en/actions/tutorials/build-and-test-code/python)、[官方 setup-python](https://github.com/actions/setup-python) 与 [Chocolatey install 文档](https://docs.chocolatey.org/en-us/choco/commands/install/)。
