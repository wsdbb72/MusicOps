# 开发与验证

应用由 PySide6 GUI、独立 worker、SQLite 状态、域名绑定的系统凭据保护和服务适配器组成。GUI 通过本地 IPC 提交任务，长任务在后台执行。

Windows 使用当前账户 DPAPI、命名管道与文件锁。macOS 使用 Keychain 保存 AES-GCM 主密钥，本地档案只存认证加密后的秘密文件；IPC 使用带密钥认证的 AF_UNIX，私有目录权限为 `0700`，socket 为 `0600`。两端均不提供明文凭据存储回退。macOS 默认档案位于用户 Application Support，不写入 `.app`。

| 位置 | 职责 |
| --- | --- |
| `src/musicops/gui` | 三个工作流入口、任务中心、配置向导 |
| `src/musicops/worker` | 本机 IPC、后台生命周期、单写者保护 |
| `src/musicops/app/pipeline.py` | 批次准备、专辑任务、阶段推进与恢复 |
| `src/musicops/providers` | 十个平台歌单、文件导入、站点、歌词、资料、下载适配器 |
| `src/musicops/clients` | qBittorrent、Navidrome、凭据与网络边界 |
| `src/musicops/library`、`media` | 索引、路径、事务、标签、NCM、音频验证 |
| `tests` | 合成样本、模拟服务与回归验证 |
| `packaging` | Windows 文件夹包 / 安装器、原生 macOS `.app`、运行包验证 |

## 本地开发

使用 Python 3.12 或以上版本创建虚拟环境，安装 `requirements.lock` 与可编辑工程。命令见 [README 开发部分](../README.md#开发验证与贡献)。

测试使用临时目录和模拟服务；媒体验证测试需要可用的 FFmpeg／ffprobe。GUI 测试可以设置 `QT_QPA_PLATFORM=offscreen`，Windows 凭据相关验证依赖当前账户的 DPAPI。避免把测试档案指向自己的实际音乐库。

`config/example.json` 展示通用配置形状。实际服务地址、鉴权与音乐目录应在本地档案中配置。可运行 `scripts/export_config_schema.py` 重新生成公开配置示例与 JSON Schema。

macOS 源码开发可使用：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r packaging/requirements-macos.txt
.venv/bin/python -m pip install --no-deps -e .
.venv/bin/musicops-gui --base "$HOME/Library/Application Support/MusicOps/dev-profile"
```

Windows 与 macOS 的依赖文件分别锁定对应构建环境。使用独立开发档案，避免与已安装应用同时操作相同私人档案。

## 证据边界

`index_library(..., metadata_only=True, checkpoint=...)` 返回元数据级只读证据，音频 SHA256 保持空值，解码状态为未运行。扫描通过检查点报告进度并响应取消或暂停；不能把快速索引当作完整音频验证。原始标签摘要有大小预算，二进制封面不会在任务结果中展开。

开始工作流应先保存可见的批次准备记录，再进入目录扫描和专辑任务创建。GUI 要能读取准备进度、失败和取消结果；异步 IPC 已接受、库扫描结束、专辑入库完成属于不同状态。

文件名与标签冲突、缺少发行信息、版本不一致、时长不明或未完成完整解码时，匹配保持待复核。在线资料候选与音频完整性验证是独立证据。

公开测试使用合成歌单和虚拟域名。新增服务适配器时应测试请求白名单、响应大小、超时、取消、鉴权失败、身份冲突与部分响应，不在测试中嵌入实际 Cookie 或密钥。

平台曲目 ID 必须保留来源命名空间，文件导入 ID 缺失时只生成本地稳定目标标识。跨平台网易云引用要经过独立的歌曲、艺人、专辑与时长匹配，不能把外国平台数字 ID 当作网易云 ID。XLSX 只读导入不得执行公式、宏、外部关系或解压到任意文件路径。格式与许可参考见 [歌单读取记录](references/global-playlists.md)。

## 打包

`packaging/build_windows.ps1` 生成 Windows 文件夹包。源码仓库不分发 FFmpeg 等第三方媒体工具二进制；如自行加入工具，应收集与具体版本匹配的许可证、来源及必要对应源码。

运行包验证应使用新建临时档案，确保首次启动、GUI／worker 通信、设置保存和失败场景均可复现。`smoke_formal.py` 与 `smoke_workflows.py` 用于原生运行包验证；具体参数可查看各自的 `--help`。构建日志、个人运行报告和配置档案属于本地内容，不提交公开仓库。

macOS 必须在对应架构的真实 macOS runner 构建，不从 Windows 交叉打包后宣称可运行。`packaging/build_macos.py --arch arm64 --output dist/macos` 生成 Apple Silicon 包；Intel runner 使用 `--arch x86_64`。脚本检查 `.app` 身份、架构、ad-hoc 签名并运行 `smoke_macos.py`，通过后生成 ZIP、SHA256 / SHA512 与提交对应的构建清单。

macOS 包目标为 15.0 及以上；当前不包含 Developer ID 签名或 Apple 公证。ad-hoc 签名验证只证明构建包的完整性，不代表 Apple 对开发者身份或恶意内容作了公证。

## 同步仓库与发布

用户可见的修复或改进完成后，同步源码仓库并发布新的 Release。CI 仅负责验证，发布过程需要单独完成，不能把“已推送提交”写成“安装包已更新”。

每次发布核对：

1. 改动、版本号、操作说明和截图一致；回归测试通过。
2. 从明确的源码提交构建 GUI、worker 和安装器，使用临时档案验收运行包。
3. 检查源码、运行包和安装器不含真实凭据、个人档案、音乐、种子缓存或私人服务地址；收集第三方许可。
4. 使用版本标签导出源码包，生成 Windows 安装包、ZIP 和对应 `SHA256SUMS.txt`。
5. 推送提交与标签，确认 Windows 测试与 macOS `arm64` / `x86_64` 构建结果；每次 Release 同步两种 Mac 包，不能把只有流水线定义当作已有运行包。
6. 创建匹配 Release，挂载两种系统中与标签一致的资产。Mac tag 发布任务会检查版本、提交、架构、自检与哈希后上传到已存在的 Release。
7. 核对服务端文件名、大小、SHA256 及 Mac 构建清单，确认公开下载可用后再宣布发布；失败的架构必须如实报告，不能标为已验证。

软件图标与工作台截图属于公开资产。截图采用合成资料，不能包含个人路径、账号、歌单、鉴权或实际私人任务。

## GitHub Actions

Windows 测试工作流使用 Python 3.12、锁定依赖与合成测试。Chocolatey 只在临时 CI runner 中安装 FFmpeg／ffprobe，不打包或上传媒体工具、运行档案与个人报告；该测试工作流本身不发布安装包。

[`macos-release.yml`](../.github/workflows/macos-release.yml) 使用 `macos-15` / `macos-15-intel` 原生矩阵。开发分支推送和手动运行保存构建产物；`v*` 标签在两种架构构建通过后，校验版本 / 提交 / 完整性，再将 Mac 包上传至同标签的已有 Release。打包验收使用临时隔离钥匙串与新档案，不读取用户音乐库，不执行真实下载或 FL 使用。构建产物和现场真实服务验收分开说明。

配置参考 [GitHub Python 测试指南](https://docs.github.com/en/actions/tutorials/build-and-test-code/python)、[官方 setup-python](https://github.com/actions/setup-python) 与 [Chocolatey install 文档](https://docs.chocolatey.org/en-us/choco/commands/install/)。
