# 性能与临时目录

MusicOps 1.0.37 的桌面和 Web 后台维护使用相同的低影响规则。

## 选择存储位置

打开“连接与设置 → 音乐放在哪里”。音乐库可以在 HDD；未启用独立临时目录时，下载和整理仍位于音乐库同级的 `MusicOps` 文件夹。

有 SSD 时，可勾选“启用独立临时下载与处理目录”，选择一个专用完整目录，建议至少有 20 GB 空间。没有 SSD 就保持关闭。程序不自动选择系统盘，也不会把现有任务或正在下载的种子强行迁移到新目录；新任务使用新设置，已有任务沿用其记录的目录。

Docker 中填写容器内路径，并在 compose 中把 SSD 文件夹挂载到该路径，例如 `/ssd-work`。仅填写宿主机路径不会创建挂载。运行账号必须有读写权限。

| 内容 | 所在位置 |
| --- | --- |
| 下载与整理副本 | 启用时在所选临时目录，未启用时在音乐库同级 |
| 验证后的成品 | 设置的音乐库 |
| 原音源备份、隔离和报告 | 音乐库同级 `MusicOps` |
| PT 做种原件 | 音乐库同级 `MusicOps/seeding` |

跨 SSD/HDD 时，整理完成后复制到最终库同盘、监听范围外的暂存区，验证后原子改名发布。只有成品校验通过、相关 qBittorrent 做种路径迁移确认完成后，才清理本任务拥有的下载、整理和发布暂存音频。备份与做种原件继续保留；失败时保留可恢复副本，不清空整个临时文件夹。

## 控制后台占用

整库维护先读取持久化 Pebble 索引和文件大小/修改时间。未变化的音频不会重新解析标签；封面和歌词侧车只在大小或时间变化时失效。歌词内容摘要在修改时间粒度无法区分时提供兜底，但会按路径分片为每周约 1/28 的抽检，不会每轮重读全部歌词。

扫描、重复指纹、补图和歌单存在性校验分别只使用一个工作通道，并在文件之间加入短节流，避免多个随机读同时抢占总线。重复项的原始文件哈希在 Windows 上运行于后台 I/O 优先级并限制为平均 8 MiB/s；歌单存在性核对只做文件 stat，不读取音频正文；PCM 解码使用低于普通优先级的独立进程，并按文件大小和时长动态计算读取倍率，避免长、高码率文件突破字节预算。第一次扫描、旧缓存版本迁移或用户主动执行整库任务时仍需要完成一次较长的索引更新，但旧记录每 200 首会把 size/mtime 快照写回数据库，后续歌单核对只做 O(1) stat 查询。

手动重复扫描是后台任务，页面会持续显示“已校验/总数”，不再依赖一个 30 秒内必须返回的长 HTTP 请求。启动阶段的歌单目录、每个 M3U、整库候选分组和歌单索引构建也会周期性检查取消信号，因此停止不会卡在“读取本地索引”。扫描每 100 组把已完成的文件指纹写回索引；合并前的文件校验和隔离复制同样遵守后台优先级、8 MiB/s 上限和取消信号。暂停调度或点击停止后，正在进行的扫描或复制最多再完成一个 256 KiB 读块就退出；已完成的检查点保留，继续后从缓存接着处理。暂停状态下不会启动新的重复扫描。

## 任务中心与索引

任务列表读取持久摘要和专辑当前阶段索引；只有执行具体任务时才加载完整清单，避免页面刷新扫描全部历史。隐藏后继阶段仍参与专辑当前阶段选择，删除后不会重新显示旧阶段。任务计数也使用提交变更驱动的摘要缓存：任务进度帧不会失效，只有工作流或任务阶段真正变化时才重建，并用 10 秒窗口合并密集更新。空闲或暂停状态下，页面轮询不会再遍历全部历史。

任务、扫描结果、歌词与封面的侧车指纹和音乐库发布记录使用 Go/Pebble 持久化。自动维护的完成时间也保存在 Pebble，重启后按上一轮完成时间继续，不会每次启动都额外排一轮。常规 6 小时维护直接读取索引中的文件集合；全库一致性核对最多每 24 小时一次，并以每个文件 10 ms 的节流运行。
