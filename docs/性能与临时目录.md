# 性能与临时目录

MusicOps 1.0.30 的桌面和 Web 后台维护使用相同的低影响规则。

## 选择存储位置

打开“连接与设置 → 音乐放在哪里”。音乐库可以在 HDD；未启用独立临时目录时，下载和整理仍位于音乐库同级的 `MusicOps` 文件夹。

有 SSD 时，可勾选“启用独立临时下载与处理目录”，选择一个专用完整目录，建议至少有 20 GB 空间。没有 SSD 就保持关闭。程序不自动选择系统盘，也不会把现有任务或正在下载的种子强行迁移到新目录；新任务使用新设置，已有任务沿用其记录的目录。

Docker 中填写容器内路径，并在 compose 中把 SSD 文件夹挂载到该路径，例如 `/ssd-work`。仅填写宿主机路径不会创建挂载。运行账号必须有读写权限。

| 内容 | 所在位置 |
| --- | --- |
| 下载与整理副本 | 启用时在所选临时目录，未启用时在音乐库同级 |
| 验证后的成品 | 设置的音乐库 |
| 原音源备份、隔离和报告 | 音乐库同级 `MusicOps` |
| PT 做种原件 | 音乐库同级 `MusicOps/seeding` |

跨 SSD/HDD 时，整理完成后复制到最终库同盘、监听范围外的暂存区，验证后原子改名发布。只有成品校验通过、相关 qBittorrent 做种路径迁移确认完成后，才清理本任务拥有的下载、整理和发布暂存音频。备份与做种原件继续保留；失败时保留可恢复副本，不清空整个临时文件夹。

## 控制后台占用

整库维护先读取持久化 Pebble 索引和文件大小/修改时间。未变化的音频不会重新解析标签；封面和歌词侧车只在大小或时间变化时失效。歌词内容摘要在修改时间粒度无法区分时提供兜底，但会按路径分片为每周约 1/28 的抽检，不会每轮重读全部歌词。

扫描、重复指纹、补图和歌单存在性校验分别只使用一个工作通道，并在文件之间加入短节流，避免多个随机读同时抢占总线。第一次扫描、旧缓存版本迁移或用户主动执行整库任务时仍需要完成一次较长的索引更新，但后续维护以数据库和增量变更为主。

维护器本身通过单通道和逐文件节流限制峰值占用。需要立即完全释放磁盘时，可直接暂停后台；已完成的索引检查点会保留，继续后从缓存接着处理。

## 任务中心与索引

任务列表读取持久摘要和专辑当前阶段索引；只有执行具体任务时才加载完整清单，避免页面刷新扫描全部历史。隐藏后继阶段仍参与专辑当前阶段选择，删除后不会重新显示旧阶段。

任务、扫描结果、歌词与封面的侧车指纹和音乐库发布记录使用 Go/Pebble 持久化。重启后直接复用索引；缓存版本升级时才需要完整重建一次。
