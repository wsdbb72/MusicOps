# Go 核心迁移契约

目标是一个 Go 后端、一套业务状态与任务执行路径，桌面和服务器共用 Web 操作界面。现有 Python 只在模块尚未替换时继续承担原功能；替代经过同等业务验证后删除旧入口。SQLite 只由独立、只读迁移工具读取，不提供 SQL 到 KV 的兼容执行层。

当前正式程序仍是 0.4.31；这个开发分支尚未接管生产数据，不能拿数据服务启动成功当作整个 MusicOps 重构完成。

## 已实现的任务边界

- Pebble 的原子条件批写只负责读条件和同步 WAL；业务请求回执由 Repository 与其状态变化一起提交，不重复维护第二套底层请求日志。
- 参数与结果按内容压缩寻址，任务头、队列、最近任务索引和状态计数不包含执行清单。结果保留到对应执行尝试，重试不会抹去上一轮结果。
- 一次领取只有一个启动身份 owner 和递增 fence。先领取，再 Begin，才允许执行外部动作。Begin 前取消可以立即结束；已经开始的操作在检查点确认暂停或取消。
- 单个阶段完成与一个或多个后继任务的创建已合并成同一个条件批写，包含参数、父子索引、状态计数和回执；后继碰撞会阻止父阶段完成，响应丢失后不会重复派生。已有取消请求时不创建后继，已有暂停请求时后继保持暂停。
- 进度采用 owner/fence/sequence 去重；重复轮询不持久保存请求回执，取消/暂停标记不会被旧进度覆盖。执行器对相同进度不反复写盘，变化进度节流；阶段改变和控制确认立即保存。
- 任务结束使用当前记录校验 owner/fence，不要求调用方仍持有早于所有进度更新的整行版本。旧执行者不能完成重试后的任务。
- 退出超时只返回“执行未退出”。在已拥有的工作真正返回之前，不释放它的状态或把任务交给新执行者。
- 原生格式2拒绝开发原型格式1，不添加无人使用的原型兼容分支；真实历史来源仍是正式 SQLite 档案。

## 必须原子完成的业务动作

工作流作业的当前阶段、领域证据、活动任务完成和后继队列边已经在**同一个条件批写**里提交，并共用原来的任务回执。不能先写“识别完成”，再单独创建搜索或处理任务。重启或响应丢失后，用同一个请求 ID 取回原回执，不会创建第二批后继。任务队列的领取成功不等于 PT、识别、文件或下载业务已经迁移。

已实现的边只有这些：

- 识别或快照作业完成时创建独立搜索作业。
- 搜索作业只有在四站分类允许时才创建处理作业：`requesting` 表示精确命中后等待获取，`fallback` 表示流媒体回退已排队。两条边都还没有下载或入库。搜索不能直接进入 `downloading`。
- 限流、网络和暂时失败会在同一搜索作业上安排重新检索，不创建处理作业，也不回退流媒体。已确认身份后，有依据的别名可以触发一次重新检索，别名本身不确认新身份。
- 同一作业从资料整理推进到验证、发布或下载前阶段。这些边只记帐，没有执行器去访问站点、文件或下载器。
- 终止为完成、失败、待核对、取消或跳过。搜索作业不能把自身直接标成完成。缺少执行器时记为待核对，不创建后继。
- 根作业或活动任务已取消时，本次提交不创建后继作业或任务。已暂停时，后继作业和任务保持暂停。
- 通用的任务完成、控制、中断不能改写带工作流归属的任务。领取、Begin、进度和未开始前释放领取仍只更新执行状态。

歌单来源曲目按唯一来源 ID 计数，并保存该集合的摘要；本地文件数和已核对命中数分开保存，不能互相推导。API、网站和目录证据只有在曲目表已核对时才能确认身份。AI 结果和日文/中文别名只作为证据留下，不能单独确认身份，也不能因此创建搜索。合成证据不能标成生产已验证。

四站名称来自配置里的 `source_order` 和 `search_status.SITE_NAMES`：`open.cd`、`dicmusic`、`orpheus`、`redacted`。网易云是另一路流媒体来源，不是这四站之一。分类要分开记录无结果、不匹配、认证、限流、访问受限、网络、暂时失败、解析或契约错误、未检索和未启用。认证失败不是空结果。版本标记冲突不能当成同一发行。未知身份不能下载，也不能自动回退流媒体。四站都未启用时保持待核对，不自动流媒体。只有歌单或补曲、身份已确认、已启用站点都明确无结果时，才自动排队流媒体；用户在核对后明确确认，才允许在认证或受限之后排队。这两种排队都不是下载成功。

AI 核对沿用现有预算：最多 20 个候选，同一搜索最多一次有依据的别名重查。未落地的模型输出不能重查，也不能确认身份。离线样本只统计分类覆盖，不是四站真实下载成功率。

下载阶段把检索无结果、匹配、认证、限流、授权、网络、下载和入库分成不同失败类。认证、限流、授权、网络、下载和入库都不会打开流媒体。只有检索侧已经得出“已启用站点都明确无结果”的回退，或者 DicMusic / Orpheus 免费令牌额度用尽且这条拒绝已经写入账本，歌单或补曲才可以排队兜底。排队仍然不是下载成功。合成音源观察必须标明 fixture，不能写成已下载或已入库。

流媒体开关按固定顺序读取：先是 Tidal、Apple Music，以及默认关闭的 Qobuz、Deezer；然后是 QQ 音乐和网易云的无损档。只有既没有已解析音源、也没有可核对资料时，最后才排歌单所在平台的文件下载器。调用方把网易云排到前面也不会改变这个顺序。生产 Python 的 `streaming.order` 仍从网易云开始；这里的顺序还没有接到执行器，也没有改那份默认配置。

DicMusic 和 Orpheus 的免费令牌只在现有条件批写里预留。余额必须是带时间的观察，未知余额不会被当成 0 或编造成可用令牌。安全余量留在余额里，不能花掉。同一资源的活动预留、以及站点上尚未对账的请求，都会挡住下一次扣费。额度用尽写一条零成本的拒绝，不静默跳过。OpenCD、RED 和网易云不能走这条令牌账本。预留、拒绝和对账都不会把任务标成已下载。

`prepare_batch`、`identify_release`、`snapshot_album`、`search_release`、`repair_album`、`process_release`、`publish_album` 只是持久命令名。数据服务不注册它们的执行器；没有执行器时任务保持不可成功完成。搜索上的限流重试已经记账。其它失败后的通用重试、已有兄弟作业的批量暂停，以及媒体、PT、文件和下载执行，仍不属于本切片。存储引擎仍是当前 Pebble 条件批写，没有更换数据库，也没有外部数据库或双写。小任务入队复用同一个 zlib BestSpeed 压缩器：同机微基准里，约 960 字节的压缩从每次新建写入器的约 1.2MB 分配降到复用后的数百字节。同步 WAL 仍在。这个读数只属于这一台 Linux，不是跨平台加速比，也不是下载成功率。

## 文件与下载副作用

队列的 started 标记只证明执行器开始，不能证明下载、FL 消费或文件发布成功。未知结果进入自动对账流程，不因经过若干分钟就释放执行权。

文件事务需要持久意图、私有暂存、完整验证、最终库同盘原子发布、做种迁移确认、拥有范围内清理和保留回滚备份。暂停点不持有数据库快照/事务；handler 返回前必须收回它启动的子工作。未实现并测试这些领域约束前，不注册真实发布/下载 handler。

FL 预约、个人免费状态和种子请求分开记账；结果未知时先只读对账。DicMusic 与 Orpheus 的令牌预留已经能在现有引擎里做条件写入，但仍只接受调用方给出的余额观察，不访问站点。账号、费用和版本选择的明确授权边界继续保留。任务恢复不等于自动允许收费下载。

## 正式发布门槛

正式发布只走 `.github/workflows/desktop-release.yml`。它在 `codex/release-*` 推送或手动 `workflow_dispatch` 时运行，不由开发分支或 pull request 触发。发布作业要同时等到 Windows、macOS 和 Linux 三份原生结果：

- Windows：`windows-latest` 上的安装器、便携 ZIP、源码 ZIP，以及原生安装和打包验收。
- macOS：`macos-release.yml` 在 `macos-15` 上只构建 arm64，并同时交出 ZIP、PKG 和 DMG。新的发布不再构建 Intel。
- Linux：`docker-release.yml` 在 `ubuntu-latest` 上构建 `linux/amd64` 镜像，做容器冒烟后推送该版本标签。`latest` 只在桌面发布作业成功之后，由后续作业推进到这次冒烟过的同一个镜像摘要。

三份结果缺一，发布作业不会把草稿改成公开 Release，也不会把标题写成 `MusicOps X.Y.Z`。已有版本拒绝覆盖。交叉编译、本机 Linux `go test`，以及 native-core 预览里的 Windows/macOS `go test`，都不能代替这条安装器和容器验收。开发分支不运行这条工作流，也不改版本号。

## 迁移与删除旧代码的顺序

1. 任务与工作流阶段的原子衔接、四站检索分类、离线发行身份，以及下载失败分类、DicMusic / Orpheus 令牌预留和流媒体顺序，已经落地。它们都不访问站点，也不把合成观察写成下载成功。媒体目录、文件事务、真实下载执行和入库仍未实现；未测试前不注册对应执行器。
2. 独立工具只读读取 SQLite v1/v2，在隔离 native 目录转换；保留原始记录、凭据引用、历史结果与恢复清单，逐表计数和逐条哈希核验，支持断点重入。
3. 用已有领域测试向量验证端到端行为。正式切换前，Windows、macOS ARM64 和 Linux amd64 容器都要在各自平台上走完 desktop-release 的原生验收。交叉编译不能代替。
4. 全部必需接口和数据核验通过后，切换唯一后端，删除旧 SQL 业务与重复入口。迁移失败保持旧档案和正在运行的正式版，不隐式清空历史。

原型数据、合成音频和测试凭据只能出现在隔离测试中，不进入正式 profile 或发行资产。
