# Go 核心迁移契约

目标是一个 Go 后端、一套业务状态与任务执行路径，桌面和服务器共用 Web 操作界面。现有 Python 只在模块尚未替换时继续承担原功能；替代经过同等业务验证后删除旧入口。SQLite 只由独立、只读迁移工具读取，不提供 SQL 到 KV 的兼容执行层。

当前正式程序仍是 0.4.31；这个开发分支尚未接管生产数据，不能拿数据服务启动成功当作整个 MusicOps 重构完成。

## 已实现的任务边界

- Pebble 的原子条件批写只负责读条件和同步 WAL；业务请求回执由 Repository 与其状态变化一起提交，不重复维护第二套底层请求日志。
- 参数与结果按内容压缩寻址，任务头、队列、最近任务索引和状态计数不包含执行清单。结果保留到对应执行尝试，重试不会抹去上一轮结果。
- 一次领取只有一个启动身份 owner 和递增 fence。先领取，再 Begin，才允许执行外部动作。Begin 前取消可以立即结束；已经开始的操作在检查点确认暂停或取消。
- 单个阶段完成与一个或多个后继任务的创建已合并成同一个条件批写，包含参数、父子索引、状态计数和回执；后继碰撞会阻止父阶段完成，响应丢失后不会重复派生。已有取消请求时不创建后继，已有暂停请求时后继保持暂停。
- 进度采用 owner/fence/sequence 去重；重复轮询不持久保存请求回执，取消/暂停标记不会被旧进度覆盖。执行器对相同进度不反复写盘，变化进度节流；阶段改变和控制确认立即保存。
- 任务结束使用当前记录校验 owner/fence，不要求调用方仍持有早于所有进度更新的整行版本。旧执行者不能完成重试后的任务。
- 退出超时只返回“执行未退出”。在已拥有的工作真正返回之前，不释放它的状态或把任务交给新执行者。
- 原生格式2拒绝开发原型格式1，不添加无人使用的原型兼容分支；真实历史来源仍是正式 SQLite 档案。

## 必须原子完成的业务动作

工作流作业的当前阶段、领域证据、活动任务完成和后继队列边已经在**同一个条件批写**里提交，并共用原来的任务回执。不能先写“识别完成”，再单独创建搜索或处理任务。重启或响应丢失后，用同一个请求 ID 取回原回执，不会创建第二批后继。任务队列的领取成功不等于 PT、识别、文件或下载业务已经迁移。

已实现的边只有这些：

- 识别或快照作业完成时创建独立搜索作业。
- 搜索作业只有在四站分类允许时才创建处理作业：`requesting` 表示精确命中后等待获取，`fallback` 表示流媒体回退已排队。两条边都还没有下载或入库。搜索不能直接进入 `downloading`。
- 限流、网络和暂时失败会在同一搜索作业上安排重新检索，不创建处理作业，也不回退流媒体。已确认身份后，有依据的别名可以触发一次重新检索，别名本身不确认新身份。
- 同一作业从资料整理推进到验证、发布或下载前阶段。这些边只记帐，没有执行器去访问站点、文件或下载器。
- 终止为完成、失败、待核对、取消或跳过。搜索作业不能把自身直接标成完成。缺少执行器时记为待核对，不创建后继。
- 根作业或活动任务已取消时，本次提交不创建后继作业或任务。已暂停时，后继作业和任务保持暂停。
- 通用的任务完成、控制、中断不能改写带工作流归属的任务。领取、Begin、进度和未开始前释放领取仍只更新执行状态。

歌单来源曲目按唯一来源 ID 计数，并保存该集合的摘要；本地文件数和已核对命中数分开保存，不能互相推导。API、网站和目录证据只有在曲目表已核对时才能确认身份。AI 结果和日文/中文别名只作为证据留下，不能单独确认身份，也不能因此创建搜索。合成证据不能标成生产已验证。

四站名称来自配置里的 `source_order` 和 `search_status.SITE_NAMES`：`open.cd`、`dicmusic`、`orpheus`、`redacted`。网易云是另一路流媒体来源，不是这四站之一。分类要分开记录无结果、不匹配、认证、限流、访问受限、网络、暂时失败、解析或契约错误、未检索和未启用。认证失败不是空结果。版本标记冲突不能当成同一发行。未知身份不能下载，也不能自动回退流媒体。四站都未启用时保持待核对，不自动流媒体。只有歌单或补曲、身份已确认、已启用站点都明确无结果时，才自动排队流媒体；用户在核对后明确确认，才允许在认证或受限之后排队。这两种排队都不是下载成功。

AI 核对沿用现有预算：最多 20 个候选，同一搜索最多一次有依据的别名重查。未落地的模型输出不能重查，也不能确认身份。离线样本只统计分类覆盖，不是四站真实下载成功率。

下载阶段把检索无结果、匹配、认证、限流、授权、网络、下载和入库分成不同失败类。认证、授权、匹配、下载和入库不会打开流媒体。限流、网络和暂时失败先按 10 分钟、30 分钟、60 分钟重试，最多三次。三次之后，只有身份已确认、流媒体已启用、场景是歌单或补曲，才自动排队兜底，原因是 `transient_recovered`。整张专辑等其它场景仍进入待核对，不自动流媒体，也不标成成功。认证失败即使重试次数用尽也仍待核对。流媒体顺序本身如果全程只有网络或限流，同样先退避重试，第三次之后进入待核对，而不是停在没有下一步的状态。排队仍然不是下载成功。合成音源观察必须标明 fixture，不能写成已下载或已入库。

流媒体开关按固定顺序读取：先是 Tidal、Apple Music，以及默认关闭的 Qobuz、Deezer；然后是 QQ 音乐和网易云的无损档。只有既没有已解析音源、也没有可核对资料时，最后才排歌单所在平台的文件下载器。调用方把网易云排到前面也不会改变这个顺序。生产 Python 的 `streaming.order` 仍从网易云开始；这里的顺序还没有接到执行器，也没有改那份默认配置。

DicMusic 和 Orpheus 的免费令牌只在现有条件批写里预留。余额必须是带时间的观察，未知余额不会被当成 0 或编造成可用令牌。安全余量留在余额里，不能花掉。同一资源的活动预留、以及站点上尚未对账的请求，都会挡住下一次扣费。额度用尽写一条零成本的拒绝，不静默跳过。OpenCD、RED 和网易云不能走这条令牌账本。预留、拒绝和对账都不会把任务标成已下载。

`prepare_batch`、`repair_album`、`process_release`、`publish_album` 仍只是持久命令名，应用不注册它们的执行器。没有执行器时任务进入待核对，错误类是 `UNSUPPORTED_COMMAND`，不能被报成成功。`identify_release`、`snapshot_album` 和 `search_release` 由 Go 应用进程注册。识别只把已提交的目录证据交给搜索。搜索对 `open.cd`、`dicmusic`、`orpheus`、`redacted` 发只读 GET：Gazelle 走 `/ajax.php?action=browse`，OpenCD 走 `/torrents.php`。下载路径不在白名单里。精确命中只进入获取队列，回执写明尚未下载、尚未入库。获取任务随后因为没有下载执行器而待核对。限流先等 10 分钟再读下一次；30 分钟和 60 分钟仍是后续档。搜索上的限流重试已经记账。其它失败后的通用重试、已有兄弟作业的批量暂停，以及媒体、PT 下载和用户库发布，仍没有执行器。存储引擎仍是当前 Pebble 条件批写，没有更换数据库，也没有外部数据库或双写。小任务入队复用同一个 zlib BestSpeed 压缩器：同机微基准里，约 960 字节的压缩从每次新建写入器的约 1.2MB 分配降到复用后的数百字节。同步 WAL 仍在。这个读数只属于这一台 Linux，不是跨平台加速比，也不是下载成功率。

## 文件与下载副作用

队列的 started 标记只证明执行器开始，不能证明下载、FL 消费或文件发布成功。未知结果进入自动对账流程，不因经过若干分钟就释放执行权。

文件事务需要持久意图、私有暂存、完整验证、最终库同盘原子发布、做种迁移确认、拥有范围内清理和保留回滚备份。暂停点不持有数据库快照/事务；handler 返回前必须收回它启动的子工作。

合成文件发布已经接到数据服务：调用方提交的 fixture 字节先进入隔离的 incoming，再复制到 staging，核对 SHA-256 后在 library 目录内改名。同一请求可以重放，不会再写一份。发布前回滚只删除 staging，不删除来源，也不创建库文件。替换会先保留旧字节，回滚时恢复旧文件。重启后未发布的意图可以继续发布。这条路径拒绝非合成输入，回执里的 `Downloaded` 和 `ProductionVerified` 保持为假。它不读取用户音乐库，也不表示站点下载已经完成。做种迁移和真实发布 handler 仍未注册。

DicMusic 与 Orpheus 的令牌预留只使用 `gazelle-balance.v1` 读到的账号余额：`personal.freeleechTokens`、`stats.tokens`、`userstats.tokens`。字段缺失是未知，不是 0；写出的 0 才是零余额。页面上的令牌数字没有账号编号时不能拿来扣费。调用方随请求传入的数字不能代替这份观察。较旧的一代观察不能覆盖较新的一代。扣费是否成功只接受带账号、资源和请求编号的 `musicops.fixture.v1` 记录；种子字节、HTTP 200 和余额差额都不会把预约改成已消耗。仓库里没有经过核对的线上扣费流水结构，真实站点的逐笔记录仍是缺口。结果未知时不重发、不自动释放。任务恢复不等于自动允许收费下载。

## 正式发布门槛

正式发布只走 `.github/workflows/desktop-release.yml`。它在 `codex/release-*` 推送或手动 `workflow_dispatch` 时运行，不由开发分支或 pull request 触发。发布作业要同时等到 Windows、macOS 和 Linux 三份原生结果：

- Windows：`windows-latest` 上的安装器、便携 ZIP、源码 ZIP，以及原生安装和打包验收。
- macOS：`macos-release.yml` 在 `macos-15` 上只构建 arm64，并同时交出 ZIP、PKG 和 DMG。新的发布不再构建 Intel。
- Linux：`docker-release.yml` 在 `ubuntu-latest` 上构建 `linux/amd64` 镜像，做容器冒烟后推送该版本标签。`latest` 只在桌面发布作业成功之后，由后续作业推进到这次冒烟过的同一个镜像摘要。

三份结果缺一，发布作业不会把草稿改成公开 Release，也不会把标题写成 `MusicOps X.Y.Z`。已有版本拒绝覆盖。交叉编译、本机 Linux `go test`，以及 native-core 预览里的 Windows/macOS `go test`，都不能代替这条安装器和容器验收。开发分支不运行这条工作流，也不改版本号。

令牌链路的正确性先于界面。单资源的余额或扣费不确定、解析失败、旧响应、短暂网络和限流，不能记成永久整站禁用。账号总余额无法拆开时，只暂停该账号新的令牌请求，并写明范围和依据。已由站点证据证明不消费令牌的获取，以及只读检索，不受这笔未对账令牌影响。真实的认证失败、站点拒绝和限流仍按站点语义保留，到期或只读复核通过后才解除暂态限制，不能为了恢复可用去清账或重发扣费请求。

核心业务和这条令牌验收通过之后、三端正式发布之前，还要完成 Go 界面的操作和视觉验收。范围是现有工作流：导航和入口找得到，常用按钮的位置和主次清楚，列表到详情和批量操作走得通，处理中、成功、失败和待核对的反馈一致，重复提交和危险操作有确认。视觉保持统一、可读，并适应不同窗口尺寸。Windows 桌面、macOS 桌面和 Docker Web 都要覆盖。这一项用实际操作和界面截图验收，不接受与功能脱节的静态页面，不恢复 Python 界面，也不删掉已经需要的能力。普通布局取舍不逐项另请确认。未完成这项，不进入正式发布。

## 迁移与删除旧代码的顺序

1. 任务与工作流阶段的原子衔接、四站检索分类、离线发行身份、下载失败分类、DicMusic / Orpheus 令牌预留、流媒体顺序，以及隔离目录里的合成文件发布，已经落地。Go 应用已经把只读检索接到调度器。DicMusic 与 Orpheus 发 `usetoken=1` 之前先读账号余额；未知余额不会发这个请求。种子保存之后令牌进入待对账，不记成已消耗。专辑文件、做种和用户库发布仍没有执行器，回执保持未下载、未入库。
2. Go 迁移器只读读取 SQLite v1/v2。它先把源文件复制到隔离临时目录，再写入调用方指定的 Pebble 目录；不写回 SQLite，也不提供 SQL 查询层。原始行进入 `archive/`。核对通过后，`Project` 再写成任务、事件、令牌、资料和其它历史文档，并单独索引 `credential_ref` 与 `vault://` 引用。逐条文档哈希回读对应原始行。中断后按游标续传。回滚领域投影只删除 `domain/`，原始归档还在。源文件指纹必须保持不变。这还没有切换正在运行的 0.4.31 档案。
3. 用已有领域测试向量验证端到端行为。正式切换前，Windows、macOS ARM64 和 Linux amd64 容器都要在各自平台上走完 desktop-release 的原生验收，并且安装包里不能再依赖 Python 运行时。交叉编译不能代替。
4. 全部必需接口和数据核验通过后，切换唯一后端，删除旧 SQL 业务与重复入口。迁移失败保持旧档案和正在运行的正式版，不隐式清空历史。

## Go 应用入口

新的进程入口是 `native/core/cmd/musicops`。它在本进程打开 Pebble、启动四个调度队列，并提供本机 HTTP。`GET /healthz` 返回 `python: false`。页面和接口都不启动 Python。浏览器基本认证的用户名是 `musicops`，口令来自 `MUSICOPS_APP_PASSWORD`，至少 16 个字符，不会写进仓库。

`POST /v1/search` 提交身份证据和检索词。Cookie 只留在进程内存里供本次只读请求使用，不写入 Pebble。受控测试把 `synthetic` 设为真，并且基址只能是 `http://127.0.0.1:端口`；观察结果带 `synthetic: true`，`production_verified` 保持为假。正式基址仍是四个站点的 HTTPS 源站。没有真实 Cookie 时返回 `AUTH_REQUIRED`，不会编造命中。

`POST /v1/archive/import` 调用上面的只读迁移。源路径必须是 `.sqlite` 文件，并且不能落在本应用的状态目录或备份目录里。

这个入口还不是桌面壳，也还不是现有 Docker 镜像里的 Web 程序。0.4.31 的 Python/Qt 与 Python Web 继续供当前正式版使用，本分支不删除它们。新进程与旧进程不要指向同一个正在写入的档案。

原型数据、合成音频和测试凭据只能出现在隔离测试中，不进入正式 profile 或发行资产。
